# 产品设计笔记：视角模型与「检索 → 消费」闭环

> 记录时间：2026-11-25
> 状态：讨论稿，未实施。本文只记录设计判断，不代表已排期。

---

## 一、一句话定位

**建立在存储之上的「个人数字资产索引层」。**

存储可以是 WebDAV、本地盘，以后可以是别的；这个产品真正有价值的不是文件本身，而是用户对文件说过的话——标签、评分、归属。由此得到第一条判断标准：

> **标签的寿命必须长于文件路径。**

---

## 二、设计原则

1. **存储无关**：只做索引与描述，不搬文件、不改文件内容。
2. **视角正交**：一个资产可以同时站在多条轴上被描述，互不干扰。
3. **自动优先，手工补充**：能自动获得的（格式、时间、尺寸、位置）绝不让人手填。
4. **检索优先于组织**：组织是为了以后能找到，产品的第一价值是「找到 + 立刻用」。
5. **标注是长期资产**：用户花在标签上的时间，不能因为挪文件夹而蒸发。

---

## 三、现有的基础（截至本次讨论已具备）

- 多服务器 WebDAV 接入（含 Range、自签证书、连接测试）
- 标签：标签分组 → 单父节点标签树；文件与标签的关联
- 标签筛选：一次一个标签，可选是否包含下级
- 文件列表：名称/类型/大小/时间/标签/收藏/关系列；批量操作
- 关系图：标签图（新增/删除子标签、展开标签下文件）、目录图（懒加载、点文件预览）、文件图（所在目录 + 所属标签，由近及远）
- 预览：图片/音频/视频/文档，支持同目录内上一张/下一张；视频转码与缓存
- 收藏、历史、主题系统

**关键结论：上面这些已经完成了「描述」和一半的「找到」，缺的是「用掉」（连续消费）。**

---

## 四、当前结构的四个问题

### 1. 路径 = 身份（最致命）

`file_tag_relation` 实际以 `(server_id, file_path)` 定位文件。后果：

- 重命名/移动目录 → 该文件所有标签失效
- 已观察到孤儿数据：`face_007_dashscope_hd.jpg` 已不在磁盘，关联仍在，展开标签时仍会出现

对个人资产库来说这是根本缺陷：**整理文件夹是常态**。

### 2. 「分组」同时扮演了视角与树根

`听 / 看 / 读 / 图` 像媒介视角；`默认分组 / 个人收藏` 不像。语义已经混在一起。

### 3. 标签树是单父节点

一个标签只能挂一处，无法表达「同一个值属于两个视角」。

### 4. 检索只支持单标签

产品的核心价值是交叉检索，但目前只能一次站一个视角，且没有计数、不能保存查询。

---

## 五、核心抽象：视角（Perspective）

**现有「标签分组」就是视角**，用户已经按这个心智在用：

| 分组 | 实际含义 |
|---|---|
| 格式 | 文件格式 |
| 图片 | 图片类别（人像/风景/截图…） |
| 位置 | 存储位置 / 拍摄地点 |
| 时间 | 时间 |
| 星级 | 评分 |

所以不需要新造概念，把「分组」升级成「视角」即可，组下的标签就是视角里的**取值**。

### 5.1 但视角分三种，不能一视同仁

| 类型 | 例子 | 单/多值 | 谁产生 | 是否可比较 | 交互 |
|---|---|---|---|---|---|
| **属性型** | 格式、大小、时长、时间、存储位置、尺寸 | 单值 | 系统自动 | 时间/大小可排序、可区间 | 只读，自动出现 |
| **数值型** | 星级、喜爱度 | 单值 | 人 | 可排序、可比较 | 点星星 |
| **标签型** | 主题、人物、歌单、场景、项目 | 多值 | 人 | 不可比较 | 勾选/拖拽 |

判断依据：如果一个视角的取值是「客观事实」，就做成属性型；如果是「人的判断」，才做标签型。

典型反例（应避免）：

- 星级做成 1–5 五个标签 → 每首歌都要打一次，必定废弃。应是 0–5 的数字。
- 时间按 `2024-07` 建标签 → 取值爆炸。应是区间查询。
- 格式、位置靠手填 → 完全无必要，文件头/路径里就有。

### 5.2 目录与标签的关系

> **目录是唯一的物理坐标轴；标签是对内容的主观描述。**
> 只不过有的描述能自动获得（格式、时间），有的必须人来说（主题、歌单）。

推论：

- 目录天然自动、天然有层级，**不需要用户维护**，可以直接投影成「存储位置」视角。
- 「位置」要细分成两个视角，别混：
  - **存储位置**：文件在哪台机器、哪个目录（系统）
  - **拍摄地点**：照片/视频的 GPS（系统，来自 EXIF）
- 目录和标签不是二选一，而是两条必须并存的轴：一条回答「它在哪」，一条回答「它是什么」。

### 5.3 命名建议

对外统一叫**视角**（比「维度」更像人话）；内部可叫 facet。

---

## 六、交叉检索

### 6.1 规则

- **视角之间 AND**
- **视角之内 OR**
- 支持 **NOT** 与 **未指定**（找没打星级的、没归歌单的）
- **实时计数**：每个取值旁显示命中数；已选其它视角时，数字应显示「与已选条件相交后」的数量

### 6.2 示例

```
视角：歌单 = 通勤        （标签型）
视角：星级 ≥ 4           （数值型）
视角：格式 = MP3         （属性型）
→ 命中 23 首，总时长 1 小时 32 分
```

### 6.3 保存查询

查询可保存为「快捷入口」/智能集合（动态结果集，不是静态清单），例如：

- 早高峰通勤（歌单=通勤 AND 星级≥4）
- 2024 家庭影像（时间∈2024夏 AND 主题=家庭聚会）

### 6.4 面板顺序

视角不是平等的：

- **事实坐标**（时间、位置、格式）用来收窄范围 → 放前面
- **意图坐标**（星级、歌单、主题）用来确认目标 → 放后面
- 最近使用、高频使用置顶

---

## 七、消费闭环：从「找到」到「用掉」

用户原话：「想听歌的时候，快速获取歌单标签中最喜欢的歌曲进行播放」。**产品最终交付的不是列表，是「立刻能用」。**

现有预览是模态弹窗：打开 → 看/听 → 关掉。对「随手看一眼」够用，对「想听歌」不够。

| 场景 | 现在 | 应该 |
|---|---|---|
| 听歌 | 点一首 → 弹窗播放 → 关掉 | 查询结果 → **播放全部** → 底部常驻播放器，边听边继续筛 |
| 看照片 | 单张预览，左右切 | 结果集 → **幻灯片**，全屏、自动播 |
| 翻文档 | 单篇预览 | 结果集内连续翻，不漏进度 |

### 7.1 队列

- 查询结果一键变成**队列**（播放全部 / 随机播放）
- 队列可编辑：从另一个视角筛出来的内容可以「加入当前队列」
- 常驻播放条在底部，不遮挡浏览；关掉预览音乐不应停
- **持久化**：队列与播放位置，下次打开可续播

### 7.2 可复用点

`FilePreview` 已经支持「同目录上一张/下一张」，音频/视频播放、Range、转码都已具备。**离「队列」只差一层「结果集 → 播放列表」的接线**，不是从零开始。

---

## 八、数据模型方向（概念级）

```
资产 Asset ──1:N── 位置 Location (server, path, mtime)
    │
    └──1:N── 断言 Assertion (facet, value, source, confidence)

视角 Facet ──1:N── 取值 Value（视角内部的树）
```

要点：

- **资产身份用内容哈希**（大文件取头尾采样 + 大小），移动/改名/换盘不丢标签
- **位置与资产分离**：一个资产可有多个位置（副本/备份），也可暂时不可用（外接盘没插）
- **断言带出处**：`source = manual / auto / import`，可带置信度；以后接 AI 不改模型，也能一键清除机器标签
- **视角带类型**：`kind`（属性/数值/标签）、`multi_value`、`auto`
- **播放状态**：队列项 + 播放进度（唯一的额外存储）

### 8.1 从现状迁移

1. `file_tag_group` → 视角表（加 `kind / multi_value / auto`），现有「听/看/读/图」直接变成标签型视角
2. 现有标签树 → 该视角的取值树（层级只在视角内部）
3. 无明确归属的标签 → 「自由标签」视角（多值、扁平）
4. `file_tag_relation` → 断言表（加 `asset_id / source / confidence`），`file_path` 降级为位置信息
5. 后台跑一次：算哈希 → 建 `asset` / `location` → 旧关联挂到 `asset_id`；同时清理孤儿关联

**关系图的新定位**：结构视图 / **资产画像解释器**（回答「这张照片为什么出现在结果里」），不是日常检索入口。日常找东西靠「网格 + 视角筛选 + 计数」。

## 十、路线图

### P0 · 打地基（2–3 周）

1. **资产身份改为内容哈希** + 位置记录 + 移动/改名自动重连
2. 清理孤儿关联，补一次全量哈希
3. **分组 → 视角**（kind / 多值 / 自动）
4. **跨视角 AND 查询 + 实时计数**
5. **结果集 → 队列**：底部播放条 + 队列面板 + 进度续播（先音频，图片幻灯片跟上）
6. 批量打标（多选后一次赋多个视角值）

### P1 · 让标签自动长出来

- EXIF / 视频 / 文档元数据抽取（后台任务）
- 属性视角可视化筛选（时间区间、星级、位置树）
- 保存查询 → 快捷入口
- 时间轴浏览、人物墙

### P2 · 抬高上限

- 相似/重复检测、连拍归组
- 地图视角
- 标签共现推荐
- 「待整理」工作流（未打标收件箱）
- 索引导出与备份（标签是最贵的资产，要能带走）

---

## 十一、待拍板的决策

1. **视角谁能建**：内置固定（格式/时间/位置/星级/目录）+ 用户自建（主题/歌单/人物），还是全开放？
2. **星级算属性还是标签**：强烈建议属性（数字），否则无法「≥4 星」。
3. **时间视角精度**：只到年/月，还是任意区间？用 EXIF 拍摄时间还是文件修改时间？
4. **「位置」指哪一个**：存储位置（目录）还是拍摄地点（GPS）？建议拆成两个视角。
5. **跨服务器**：一个歌单的歌分散在两台机器，队列能否混播？
6. **播放是否常驻**：接受底部长期有播放条吗？还是坚持弹窗式？
7. **现有标签树**：平滑迁移，还是趁机重构（当前树已经有些混）？

---

## 十二、明确不做

- 不做编辑器（不改文件内容）
- 不做同步 / 备份服务（只做账本）
- v1 不做团队权限与共享
- v1 不做全自动 AI 打标（先把 EXIF 与规则吃干净，模型里留 `source=auto` 接口）
- 不做无限层级标签（层级只在视角内部，建议 ≤ 4 层）

---

## 十三、如果只做一件事

> **把文件身份从路径改成内容哈希，并顺手支持跨视角 AND 查询。**

前者保住已有数据，后者兑现产品承诺。其余都可以往后排。

---

## 十四、一句话收束

> **视角负责「怎么描述」，组合负责「怎么找到」，队列负责「怎么用掉」。**

三者缺一，产品就会退回「带标签的文件管理器」。

# 附：文件夹重复检测（去重整理）

> 决策时间：2026-11-26

## 定稿参数

| 项 | 决策 |
|---|---|
| 用途 | **去重整理**（不是备份校验） |
| 重复处理 | **不删除**，只出报告与证据 |
| 默认强度 | **L2**：大小 + 头尾各 4MB 采样哈希（≤ 8MB 的文件直接全量） |
| 写权限 | **无**，纯只读 |
| 比较范围 | **只比两个目录**（不做整服务器对整服务器） |
| 路径基准 | 暂以**左边**为准 |

## 算法

1. 递归列出两边文件 → `(side, relPath, size, mtime)`
2. 排除：0 字节文件、系统文件（`.DS_Store` / `Thumbs.db`）、可选最小尺寸
3. 按 `size` 分桶，**只保留成员数 ≥ 2 的桶**（其他不可能重复）
4. 桶内计算 L2 指纹 → 再分组
5. 组内成员 ≥ 2 → 一个**重复组**；标注左/右、跨边/同边
6. **可回收空间 = 文件大小 × (成员数 − 1)**（去重场景最有价值的数字）
7. 按可回收空间降序排列

## 安全设计

- **L2 只是「候选」，L3 才是「确认」**：每个重复组可手动复核（全量哈希），报告标注「已确认 / 未确认」
- 系统永不删除文件；导出 CSV / 复制路径，由用户自己处理
- **检测路径重叠**：若一边是另一边的子目录（同一 server），拒绝比较，避免自己跟自己比出「重复」
- 两边完全相同（同 server 同路径）时直接拒绝

## 界面

```
重复组 28 个 · 涉及 61 个文件 · 可回收 3.4 GB
[只看跨边 ☑] [只看 ≥10MB] [已确认 ▾]

#1  3 个副本 · 220 MB · 可回收 147 MB · 跨边
   左   2024/IMG_001.jpg         220MB  2024-07-01
   右   2024/IMG_001.jpg         220MB  2024-07-02
   右   2024/copy-IMG_001.jpg    220MB  2024-07-02
   [复核] [并排预览] [复制路径]
```

- 组按「左边成员路径」排序；只有右边成员的分到「仅右侧重复」分区
- 支持导出报告；「已确认 / 忽略」状态存本地账本，不改动文件

## 边界与坑

| 情况 | 处理 |
|---|---|
| 同名不同大小 | 落在不同桶，各自判断（正确，去重不看名字） |
| 同名同大小但内容不同 | L2 判定不同，不成组（不会误报为重复） |
| 0 字节文件 | 默认排除，否则全部互相同 |
| Unicode NFC/NFD | 比较前统一 NFC，否则同一中文名会判成不同 |
| 网络中断 / 权限不足 | 该文件标记「未完成」，可重试，不阻塞整体 |
| 小文件 | ≤ 8MB 时 L2 = 全量哈希，成本可忽略 |

## 工程约束

- **必须异步**：建任务 → 进度 → 结果分页
- **限流**：对两侧 WebDAV 限并发与带宽
- **缓存**：任务可暂停续跑；哈希后续落 `asset.hash`，第二次比较几乎零成本
- **成本可知**：开跑前给出「预计读取 X GB / 约 N 分钟」

## 阶段

**P0**：L1 分桶 + L2 指纹 + 重复组列表 + 可回收空间 + 复核（L3）+ 导出 CSV
**P1**：任务持久化/续跑 + 哈希缓存 + 忽略规则 + 最小尺寸筛选
**P2**：接入资产索引（「重复度」成为视角）+ 定时校验 + 多目录批量比对
